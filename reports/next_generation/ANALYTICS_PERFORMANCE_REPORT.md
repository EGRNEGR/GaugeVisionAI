**Проект:** GaugeVision AI Next Generation  
**Ветка:** `next-gen/analytics-validation`  
**Профилируемые модули:** `app/predictive_analytics.py`, `app/modernization_optimizer.py`, `app/ilp_solver.py`, `app/spec_generator.py`, `app/main.py`

## 1. Выявленные узкие места и реализованные оптимизации

При профилировании исходной реализации на масштабах 36–1000 приборов были выявлены 3 реальных узких места:
1. **Блокировка asyncio event loop (`lag_max = 1 212,6 мс`):** вызовы `optimize_modernization_budget(...)`, `PredictiveAnalyzer.overview(...)` и `DispatchAnalyzer.overview(...)` выполнялись синхронно в `async def` обработчиках FastAPI (`app/main.py`), замораживая `/api/health`, WebSocket-рассылку и Modbus TCP сервер на время расчёта.
2. **Квадратичные Python-циклы в `_theil_sen_slope` и `_mann_kendall_test`:** при 60 точках на прибор `analyze_series` занимал **10,5 мс/прибор** (`10,50 с` на 1 000 приборов).
3. **Отсутствие кэширования сводки и ограничения конкурентных расчётов оптимизатора:** повторные обращения HMI к `/api/predictive/overview` каждый раз пересчитывали все ряды, а параллельные запросы к `/api/optimizer/solve` могли перегрузить CPU.

**Внесённые изменения (`app/predictive_analytics.py`, `app/main.py`):**
- Векторизация `_theil_sen_slope` и `_mann_kendall_test` через `numpy.triu_indices` — ускорение на **~30%** без изменения математических результатов (`10,50 → 7,37 мс/прибор`).
- Выделенный ограниченный пул потоков `service.analytics_executor = ThreadPoolExecutor(max_workers=2, thread_name_prefix="analytics")` для вынесения прогнозной аналитики, диспетчеризации и 0-1 ILP-оптимизатора за пределы asyncio event loop.
- Короткоживущий TTL-кэш сводки `service._predictive_cache` (TTL = 5 с, макс. 16 ключей, обход при `persist=True`).
- Ограничение конкурентных расчётов оптимизатора (`asyncio.Semaphore(2)`, таймаут ожидания 2,5 с -> HTTP `429 Too Many Requests`), жёсткий лимит `time_limit_s ≤ 5,0 с` и кооперативная отмена `cancel_event` при отмене запроса.

## 3. Доказательство неблокирующей работы asyncio event loop (N = 500)

Во время одновременного запуска прогнозного пересчёта и оптимизации портфеля на **500 приборах** (с кривой Парето) параллельно измерялись:
1. джиттер/задержка asyncio event loop (`target tick = 10 мс`);
2. число непрерывных циклов обновления регистров `ModbusTcpGateway` (`каждые 50 мс`).

| Режим выполнения | Общее время (мс) | Замеров петли | Тиков Modbus за время задачи | Event loop lag p50 (мс) | Event loop lag p95 (мс) | Event loop lag MAX (мс) |
|---|---:|---:|---:|---:|---:|---:|
| **ДО: синхронно в event loop** | 1 220,9 | 8 | 3 (заморозка!) | 5,56 | 790,41 | **1 212,63** |
| **ПОСЛЕ: `analytics_executor`** | 1 220,1 | 61 | **24 (без пропусков)** | 6,07 | **21,53** | **23,85** |

Вынос расчётов в ограниченный пул потоков снизил максимальную блокировку event loop в **50,8 раза** (`1 212,6 → 23,85 мс`), полностью устранив заморозку оперативного мониторинга, WebSocket и Modbus TCP.

## 5. Оставшиеся ограничения и рекомендации на масштаб > 500 приборов

- При `N = 1000` полный пересчёт всех 1 000 приборов в `PredictiveAnalyzer.overview` занимает ~7,37 с на 1 CPU-ядре. Для парков `N > 300` рекомендуется инкрементальный пересчёт в фоновом цикле батчами (например, по 100 приборов за тик) и установка опционального HiGHS (`scipy`) для мгновенного построения кривой Парето (`include_frontier=True`).
- На Windows в Python с GIL фоновый поток NumPy/Python может вносить краткий джиттер `~20–24 мс` в event loop (см. таблицу выше); для строгих SLA `< 5 мс` при `N ≥ 1000` на промышленном сервере Linux целесообразно выносить оптимизатор в `ProcessPoolExecutor` (1–2 воркера).

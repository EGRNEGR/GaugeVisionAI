# Отчёт о часовом soak-тесте GaugeVision AI (CPU)

Работающий сервер `run.py --demo` нагружался непрерывно 3603 с на CPU (`CUDA_VISIBLE_DEVICES=""`, `GAUGEVISION_DEVICE=cpu`). Нагрузка: пять CV-каналов, клиенты HMI, сторонний MQTT-брокер и RTSP-сервер с периодическими реальными отказами. Длительность не сокращалась, результаты не экстраполировались. Утечек памяти, потоков, дескрипторов и соединений не обнаружено. Очередь Store-and-Forward после каждого отказа опустошалась, все 2282 записи доставлены в брокер без потерь и дублей. Ошибок в журнале сервера и в ответах API нет.

Итог по исходным критериям скрипта — 15 из 16, по исправленным — 17 из 17 (раздел 4). В ходе прогона найден дефект наблюдаемости NEW-12 (раздел 5).

Доказательства: `evidence/soak/` — `samples.jsonl` (239 замеров через 15 с), `summary.json` (итог прогона, без изменений), `summary_reanalyzed.json` (пересчёт критериев по тем же замерам), `server.log`, `amqtt_broker.log`, `server_process.json`. Скрипт: `tests/soak_real_pipeline.py`.

## 1. Чем soak Antigravity отличался

Скрипт `soak_60min.py` из журнала Antigravity (`evidence/antigravity/scripts_original/`) поднимал отдельные классы в одном процессе, без HTTP-сервера, клиентов и реальных отказов. Часового прогона Antigravity не выполнял. Новый скрипт нагружает настоящий процесс сервера и снимает метрики с дочернего процесса интерпретатора: на Windows `python.exe` из venv — лаунчер, сервер работает в его потомке.

## 4. Критерии и их исправление

Исходный вердикт скрипта — `SOAK FAILED` (сохранён в `summary.json`): не прошёл критерий `docx_generated_valid`. В самом критерии была ошибка: генерация идёт на отметках 600, 1200 … 3000 с, а на 3600 с прогон уже останавливается, то есть внутри часа их пять. Критерий же требовал `int(3603 // 600) = 6`. Сервер выполнил все 5 запросов, все документы валидны, брака 0.

Вторая ошибка — критерий утечки памяти по RSS. На Windows он проходит из-за урезания рабочего набора, даже если утечка есть. В скрипт добавлен критерий по private bytes.

После исправления критерии пересчитаны по тем же сохранённым замерам (`--reanalyze`, итог — `summary_reanalyzed.json`). Повторный часовой прогон ради этого не выполнялся.

## 5. Дефект, найденный в прогоне (NEW-12)

При настоящем падении брокера `sync_state` очереди S&F оставался `SYNCING`: состояние `BUFFERING` ставилось только при симуляции обрыва из интерфейса. На вкладке архитектуры пульт показывал «ДОСЫЛКА ПАЧКАМИ» и «ДОСТАВКА АКТИВНА», хотя очередь росла, а брокер не подтверждал доставку. Данные при этом не терялись. Исправление и его проверка описаны в `DEFECT_RESOLUTION_REGISTER.md` (NEW-12).

## 6. Ограничения

- Прогон один, длительность — 1 ч. Тренд private bytes к концу выходит на плато, но поведение на сутках и неделях этим прогоном не подтверждается.
- Только CPU. На GPU soak не выполнялся по аппаратному ограничению стенда (RTX 5060 Laptop, ошибки WHEA); сценарий для RTX 3090 — `tests/gpu_validation_3090.py`.
- Отказы брокера и RTSP — остановка процессов на том же узле, а не потеря пакетов в сети. Сетевые потери и задержки не эмулировались.

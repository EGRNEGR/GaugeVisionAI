# Полный отчёт о повторной приёмке и завершении устранения дефектов GaugeVision AI

## 1. Исходное положение

Независимый аудит Gemini (`reports/audit/`) оценил систему в 60,3 из 100. Соответствие ТЗ — 60,7 % по 75 требованиям, найдено 22 дефекта, в том числе один P0 (тихая потеря тревог при отказе MQTT-брокера) и семь P1. Затем Antigravity устранял дефекты и заявил, что все 22 закрыты. Повторная приёмка должна была проверить эти заявления по исходной методике, довести работу до конца и выставить оценку только по подтверждённым результатам.

Материалы аудита в `reports/audit/` не изменялись. Работа шла в ветке `remediation/acceptance`. Коммит `60908e7` — неизменённый снимок состояния после Antigravity, всё после него сделано в ходе приёмки.

## 2. Что было проверено в работе Antigravity

### Восстановление контекста

Журнал Antigravity (`~/.gemini/antigravity-cli/brain/695f6dc6-…`) прочитан полностью: аудит — шаги 764–883, устранение — 900–1363. Скрипты и доказательства из его временного каталога перенесены в `evidence/antigravity/` без абсолютных путей. Бенчмарк переносимо оформлен как `tests/benchmark_cpu.py`. Последняя задача Antigravity (`task-1363`, повтор `audit_05`) завершилась с кодом 0.

## 4. Как проверялось

Принцип — проверять гарантии по исходным критериям аудита, а не текущее поведение кода, и где можно — через независимые реализации:

- **Исходные аудиты Gemini без изменений** на финальном коде, с явно оговорёнными условиями запуска (`evidence/original_audit_rerun/`).
- **Независимый набор тестов** `tests/test_acceptance_independent.py` (21 проверка), написанный отдельно от тестов Antigravity: SHA-256 у получателя, идентичность кадров клипа, SQL-статистика против эталонного расчёта, матрица RBAC, промышленный режим и миграция старой БД в отдельных процессах.
- **Сторонние реализации протоколов**: реальный RTSP (mediamtx + ffmpeg, сверены по SHA-256 с официальными релизами), брокер amqtt с реальными остановками, клиент pymodbus.
- **Чистая offline-установка** в новом venv из локального wheelhouse, с аудит-хуком Python на все сетевые вызовы процесса сервера.
- **Строгий браузерный E2E** с RBAC на трёх разрешениях.
- **Часовой soak** работающего сервера на CPU: пять CV-каналов, клиенты HMI, реальные отказы.
- **Оборудование**: USB/UVC-камера, локальная LLM, RTX 5060 Laptop (по просьбе пользователя, с контролем температуры).

## 5. Ключевые механизмы после приёмки

### Store-and-Forward и доставка в SCADA

MQTT 3.1.1 QoS 1: `publish()` возвращает успех только после PUBACK. На брокере amqtt с реальными остановками — 0 потерь и 0 дублей в двух интеграционных прогонах (113/113, 117/117) и в часовом soak (2282/2282 при 6 остановках). Кадры тревог доставляются отдельным сообщением, SHA-256 у получателя совпал. После подтверждения байты кадра в очереди не хранятся. Очередь ограничена по строкам, мегабайтам и диску, при переполнении вытесняется телеметрия, тревоги сохраняются. Реальный отказ канала оператор видит как буферизацию через 6 с после остановки брокера.

### Диспетчерская аналитика

Производные считаются по фактическим меткам времени, ряд прореживается до 1,5 с, скачок ниже 1,5 % шкалы не считается гидроударом. Перегрузка накапливается по факту (90 тиков по 2 с — 3,00 мин), срабатывания считаются по реальным окнам 12 и 24 ч. Индексы разделены: пар на объективе снижает `optical_health` до 40 %, техсостояние остаётся 100 %, загрязнённая камера не даёт рекомендации модернизации.

### Генератор ТЗ

Период меняет выборку из SQLite. Агрегация выполняется в SQL оконными функциями, интервалы без связи дольше 600 с исключаются. Исправное оборудование даёт пустую ведомость и CAPEX 0. Единичное срабатывание попадает в ведомость без CAPEX, в ТЗ включаются регулярные перегрузки (не меньше трёх за период). Экономика учитывает OPEX, при CAPEX 0 окупаемость не рассчитывается. Автогенерация по триггеру персистентна, не дублируется в пределах cooldown, переживает перезапуск, документ доступен оператору через HMI. Обогащение локальной LLM проверено на реальной модели: чисел вне исходных фактов нет, экономика и правовое разграничение не меняются.

### CV-конвейер

На 27 эталонных кадрах точность не изменилась (MAE 0,0125 МПа на шкале 0–16). Перекрытие 44 % отклоняется, а не даёт ложного показания. На реальном RTSP — 80/80 показаний в пределах ±0,35 МПа. На GPU показания совпадают с CPU. Достоверность низкого качества кадра (пар, блик, заморозка, перекрытие) вычисляется по пикселям, без обходов через `injected_fault`.

### Безопасность

RBAC на 53 из 64 REST-маршрутов (без него остаются только страницы, вход и выход, `health`, публичное подмножество `meta` и сертификат), WebSocket пульта — с перепроверкой сессии. PBKDF2 для паролей, в БД только SHA-256 токенов, Fernet для URL камер. Блокировка перебора: 5 попыток за 300 с. Вне деморежима стендовые пароли отклоняются. 13 вариантов SSRF и 9 вариантов Path Traversal отклоняются, пароль RTSP не попадает в API, БД и журналы. Подробности — в `SECURITY_REVALIDATION.md`.

### Автономность

Чистая установка 61 пакета из wheelhouse без доступа к индексам, затем запуск всей системы. Аудит-хук зафиксировал 0 обращений к нелокальным адресам: DNS-запросы ultralytics и UDP-проба в `run.py` устранены. Подробности — в `OFFLINE_INSTALLATION_REPORT.md`.

## 9. Ограничения приёмки

- CV проверена на синтетических эталонных кадрах, реальном RTSP-потоке с отрендеренным прибором и камере без прибора в кадре. На фотографиях реальных цеховых КИПиА точность не измерялась.
- Интеграция со SCADA проверена на независимых реализациях MQTT и Modbus, не на Ignition или MasterSCADA.
- Soak — 1 ч на CPU. GPU — 5 минут на ноутбучной RTX 5060, RTX 3090 не испытывалась.
- Docker-образ не собирался (нет Docker Engine), Linux и Astra/RED OS не проверялись.
- Сетевые потери пакетов не эмулировались: отказы — это остановка процессов на том же узле.

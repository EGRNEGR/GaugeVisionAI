## 3. Аудит Трека №2 — Архитектурная видеоаналитика (Раздел 5)

1. **Менеджер видеоисточников (`stream_manager.py` / `streamer.py`):**
   - Подтверждены `video_file`, `phone_ws`, стендовые OpenCV-потоки и неблокирующее поведение при недоступном RTSP (`event_loop_max_lag_ms = 10,8 мс`).
   - Нагрузочное тестирование на CPU показало устойчивое масштабирование на 1 / 2 / 4 / 8 каналах (`10,27 / 15,68 / 31,38 / 57,38 FPS`, p50 `25,5–32,3 мс`, 0 ошибок) и реальную изоляцию при остановке одного канала (`evidence/warm_1ch_isolation.json`).
   - Физическая USB-камера и живой внешний RTSP-сервер в стенде отсутствовали (`REQ-VA-03` = `NOT VERIFIED`, `REQ-VA-01` = `PARTIAL`).
2. **Диагностика видеосигнала (`FrameQualityAnalyzer`):**
   - На модифицированных кадрах *без* флага `injected_fault` детектор обнаружил темноту (`luma=14,1`), полное перекрытие (`luma=4,0`), запотевание/пар (`sharpness=1,1–3,5`), блики (`glare_pct=25,7%`), заморозку (12 идентичных кадров) и восстановление (`evidence/track2_audit_results.json`).
   - **Обнаружены дефекты (`DEF-11`):** 50% чёрное перекрытие половины объектива пропущено (`ONLINE`, `quality_score=100,0`); полностью статичный кадр без сенсорного шума даёт ложную заморозку; метод `record_drop()` нигде не вызывается (потеря пакетов фиктивна); детектор содержит ручные обходы `if injected_fault == ...`.
3. **Adaptive FPS (`AdaptiveFpsController`):**
   - Фактическое снижение нагрузки CPU подтверждено: `24,4%` в `eco_idle` (1 FPS) против `83,6%` в `event_burst` (6 FPS) — **реальная экономия 70,8% CPU** (`evidence/perf_soak_fault_results.json`).
   - **Ограничение (`DEF-12`):** отсутствует быстрый motion/frame-diff пробуждающий триггер в `eco_idle`, поэтому переходные импульсы длительностью `< 1,0 с` (например `0,35 с`) между опросами пропускаются.
4. **Кольцевой буфер инцидентов (`IncidentRingBuffer`):**
   - Для одиночного инцидента `pre`-кадры строго предшествуют триггеру, а `post`-кадры следуют после него.
   - **Дефект (`DEF-10`):** при срабатывании второго инцидента до завершения добора `post`-кадров первый инцидент перезаписывается и теряется (`concurrent_incident_1_lost: true`); архивы хранятся только в RAM.
5. **Store-and-Forward (`store_forward.py`):**
   - Фактический `PRAGMA journal_mode` = **`wal`**; сценарии A, B, D (рестарт с сохранением 15/15 записей), E (повторный обрыв 40+10=50) и гонка `enqueue` vs `flush` (0 дублей, строгий порядок) пройдены.
   - **Блокирующий дефект P0 (`DEF-01`):** при реальном отказе MQTT-брокера (`MQTT_ENABLED=1`) `MqttAsyncAdapter.publish()` возвращает `True`, и очередь помечает сообщения как `sent`, **тихо теряя данные**.
   - **Критический дефект P1 (`DEF-06`):** `frame_blob` сохраняется в SQLite, но никогда не передаётся в `deliver_cb`; `SF_MAX_QUEUE_ROWS` чистит только `sent`, позволяя `pending`-очереди расти без ограничений (сценарий G: 60 строк при лимите 30).
   - **Модель гарантий:** строго **at-least-once** (сценарий F при потере ACK дал `1` дубликат, `DEF-21`).
6. **REST API, WebSocket/SSE, MQTT, Modbus TCP:**
   - Все новые REST-маршруты, WebSocket `/ws/dashboard` и SSE `/api/events/stream` работают; `PATCH` с JSON `NaN` вызывает необработанный HTTP `500` (`DEF-09`).
   - Modbus TCP сервер (FC `0x03`/`0x04`) и MQTT 3.1.1 клиент подтверждены по реальному TCP-сокету, но выявлены протокольные пробелы (`DEF-13`: нет проверки `unit_id`, `stale=0.0`, MQTT без `PINGREQ`/Auth/QoS 1). Стыковка с реальным Ignition/MasterSCADA не проверялась (`NOT VERIFIED`).

## 4. Аудит Трека №1 — Умная диспетчеризация и генерация ТЗ (Раздел 6)

1. **Математическая проверка `dispatch_analyzer` (12 контрольных сигналов, `evidence/track1_security_audit_results.json`):**
   - `rate_per_min` на линейном росте/спаде `±6,0 МПа/мин` (1 Гц) совпадает с эталоном (`+6,0 / -6,0`); `_compute_chatter` на осцилляции `±0,5 МПа` выдаёт `8,33%` и класс `instrument_degradation`; деление на ноль при дубликатах временных меток защищено (`max(1.0, dt)`).
   - **Выявлены существенные дефекты (`DEF-08`, `DEF-14`):**
     - мгновенный вход в `alert` на `t=0` начисляет фантомные **`+6,5 мин`** перегрузки (`+2,5 мин` для `warning`);
     - `trips_24h` жёстко вычисляется как `trips_shift * 2` без реального 24-часового окна;
     - `peak_rate_per_min` делит на фиктивный шаг `15.0 / (N-1)` мин даже для 1 Гц ряда из памяти;
     - `_BENCH_DIAGNOSTIC_PROFILES` искусственно подставляет `chatter_pct=3,8%` и `overload_min_base` поверх плоской телеметрии симуляции;
     - `Health Score` смешивает техсостояние узла с качеством камеры: туман/низкий confidence `0,20` роняет `Health Score` полностью исправного узла до **`72,0%`**.
2. **Генератор документации `spec_generator` + `docx_builder` (9 сценариев):**
   - OpenXML `.docx` (`129,8 КБ`, 4 встроенных JPEG, колонтитулы, штампы, таблицы, валидный XML при XSS-вводе) и `.md` (`27,4 КБ`) генерируются за **33,8 мс** и **0,6 мс** соответственно, полностью воспроизводимы в детерминированном режиме; протокол LLM-интеграции и graceful fallback (HTTP 500, битый JSON, таймаут) подтверждены против локального mock-сервера.
   - **Выявлены критические дефекты достоверности (`DEF-03`, `DEF-04`, `DEF-17`):**
     - `period` (`12h` vs `30d`) меняет **только строку заголовка** — аргумент `events` не используется, таблица `readings` SQLite не читается;
     - на 100% здоровом оборудовании в дефектную ведомость и ТЗ принудительно попадают 3 прибора с CAPEX `316 920 ₽`;
     - на пустых данных (`CAPEX = 0`) выводится окупаемость `1 мес.`;
     - при несуществующем фильтре цеха происходит тихий fallback на `all_items[:6]`;
     - цены оборудования, экономия `38 000 ₽/год` и конкретные бренды захардкожены без OPEX и пользовательского ввода, а на синтетических доказательных кадрах нанесён фиктивный штамп `CONF=0.94`.

## 5. Регрессионный аудит компьютерного зрения (Раздел 7)

Источник: `reports/audit/evidence/cv_regression_results.json`.
- `models/gauge_yolov8.pt` загружается автономно за `6,14 с` (CPU).
- На 17-точечном синтетическом прогоне `0–16 МПа` CW (включая переход через `0°/360°`): **MAE = 0,0125 МПа (0,078% шкалы), RMSE = 0,0146 МПа, 0 пропусков**. CCW `0–100%`: MAE = **0,083%**. Отрицательный диапазон `-100..0 кПа`: MAE = **0,093 кПа**. Перспектива `0,72`: ошибка **0,261 МПа**.
- Пустой кадр, мёртвая зона `90°` и сильный блик безопасно отклоняются (`valid=False`).
- **Дефекты:** (1) `DEF-02` — затенение переменной `level` в `app/vision.py:888` штампует зелёный `CRITICAL` на нормальных кадрах; (2) `DEF-15` — 44% частичное перекрытие даёт ложное показание `2,50 МПа` вместо `12,0 МПа` (`conf=0,355`); несколько приборов в одном кадре не поддерживаются.
- Валидация на реальных фотографиях цеха и GPU-бенчмарк — `NOT VERIFIED`.

# Техническое задание агенту: REQ-API-07 — стыковка GaugeVision AI с реальной SCADA по Modbus TCP

## 1. Цель и контекст

GaugeVision AI — система распознавания показаний стрелочных приборов (FastAPI, Python 3.12). В ней уже есть
промышленный шлюз Modbus TCP (`app/scada_gateway.py`, класс `ModbusTcpGateway`), но в матрице требований
пункт REQ-API-07 «Подтверждённая стыковка с реальными SCADA-системами Ignition или MasterSCADA» имеет статус
NOT VERIFIED: до сих пор шлюз проверялся только сторонними библиотеками (pymodbus, amqtt), а не настоящей SCADA.
Текущая оценка проекта — 96,65/100 (72 PASS / 1 PARTIAL / 2 NOT VERIFIED; второй NOT VERIFIED — REQ-CV-05,
им параллельно занимается другой агент, его не трогай).

Задача — развернуть локально настоящий экземпляр SCADA **Ignition 8.3** (Inductive Automation; альтернатива —
MasterSCADA 4D, только если пользователь сам об этом попросит), подключить его к существующему шлюзу Modbus TCP
GaugeVision в изолированном лабораторном контуре **только на чтение**, построить в SCADA мнемосхему, проверить
реальный обмен (совпадение значений, живые изменения, обрыв и восстановление связи, индикацию устаревших и
недостоверных данных), расширить карту регистров с полной обратной совместимостью, сохранить проект SCADA,
скриншоты и численные результаты, написать отчёт и честно пересчитать оценку.

## 5. Порядок работ

1. **План.** Создай `reports/industrial_validation/SCADA_PROGRESS.md` с планом и обновляй по ходу.
2. **GaugeVision в демо-режиме с шлюзом:**
   ```
   set GAUGEVISION_MODBUS_ENABLED=1 & set GAUGEVISION_MODBUS_HOST=127.0.0.1 & set GAUGEVISION_MODBUS_PORT=15020
   set GAUGEVISION_DEVICE=cpu & set CUDA_VISIBLE_DEVICES=
   python run.py --demo --device cpu
   ```
   (или эквивалент в bash). Проверь `GET /api/scada/modbus/registers` (нужна авторизация оператора — посмотри
   `app/auth.py` и демо-учётки в `docs/DEMO_DEFENSE_GUIDE.md`), что регистры живые.
3. **Ignition: устройство Modbus TCP** (Modbus Driver v2 входит в дистрибутив): Hostname `127.0.0.1`, Port `15020`,
   Unit ID `1`. Разберись с адресацией драйвера (1-базная/0-базная, опция Zero-Based Addressing, порядок слов —
   Reverse Word Order) и подтверди её фактом: значение прибора 0 в Ignition должно совпасть с регистрами 0–1 в
   `/api/scada/modbus/registers`; ошибка «на единицу» — частая, проверь на нескольких приборах.
4. **Теги:** папка `GaugeVision` — для каждого из 36 приборов: значение (Float), статус (Int), Health (÷10),
   плюс системный блок 900–905 и новые регистры (п. 5). Все теги — read-only. Производные (Expression) теги:
   «связь есть/нет» по качеству тегов устройства, «данные устарели» по heartbeat (п. 5), «нет данных» при NaN.
   Экспортируй теги в JSON.
5. **Расширение карты регистров с обратной совместимостью** (`app/scada_gateway.py` + тесты):
   существующие адреса 0–799 и 900–905 и их смысл не менять. Добавь, например: в системный блок 906 — heartbeat
   (счётчик, растёт на каждой синхронизации, переполнение через 65535 → 0), 907–908 — unix-время последней
   синхронизации (uint32), 909 — версия карты регистров; отдельный расширенный блок для приборов (поднять
   `MAX_REGISTERS`, например до 4096, база `2000 + idx*8`): возраст показания в секундах (uint16 с насыщением),
   уверенность распознавания ×1000, битовые флаги (камера на связи, циферблат найден, показание достоверно,
   калибровка задана), unix-время последнего достоверного показания (uint32). Точную раскладку выбери сам, опиши
   в `docs/MODBUS_REGISTER_MAP.md` и в docstring класса. Тесты pytest: старые адреса выдают те же значения, что
   до изменения (регрессия), новые — корректные, запросы за границей карты — исключение 0x02, чужой unit id — 0x0B.
6. **Perspective-мнемосхема** «GaugeVision — пульт» в проекте Ignition (например, `GaugeVisionLab`):
   плитки 36 приборов (позиция, значение с единицей, цвет статуса в духе ISA-101 — серый фон, цвет только для
   отклонений, «нет данных» вместо 0 при NaN), индикатор связи со шлюзом и возраст heartbeat, счётчики системного
   блока, тренд 2–4 приборов (Power Chart/Time Series). Создавать через Designer (скачивается со шлюза, Designer
   Launcher) или файлами проекта 8.3 (`data/projects/<проект>/com.inductiveautomation.perspective/views/.../view.json`)
   с пересканированием проекта — как надёжнее получится.
7. **Испытания** (каждое — с численным результатом, временем и скриншотами Perspective, снятыми Playwright
   headless 1920×1080 с `http://localhost:8088/data/perspective/client/<проект>`):
   - связь установлена: состояние устройства Connected, качество тегов Good;
   - совпадение значений: не менее 10 приборов (лучше все 36), серия замеров не менее 30 минут — значения,
     прочитанные Ignition (журнал SCADA: Tag Historian/встроенный историк 8.3 или gateway timer script, пишущий CSV),
     против `/api/instruments` / снимка регистров GaugeVision в те же моменты; расхождение — в пределах
     округления float32 и периода опроса; таблица и статистика;
   - живые изменения: тренд меняется вместе с демо-сценарием; смена статусов OK → WARNING → CRITICAL;
   - STALE/недостоверно: прибор без данных — NaN и статус 3 в SCADA отображаются как «нет данных», а не 0;
   - обрыв связи: остановить процесс GaugeVision (или закрыть порт) → время до индикации обрыва в SCADA,
     качество тегов Bad, мнемосхема показывает «нет связи»;
   - восстановление: запуск GaugeVision → время автоматического переподключения, значения снова совпадают;
   - «зависание» без обрыва TCP: heartbeat перестаёт расти → SCADA помечает данные устаревшими;
   - сценарий обрыва канала АСУ ТП в демо (Store-and-Forward): регистры 904/905 в SCADA.
8. **Артефакты в репозитории:**
   - `integrations/ignition/` — экспорт проекта Perspective (zip или файлы проекта), экспорт тегов JSON, описание
     подключения устройства (без паролей), `README.md` — как воспроизвести с нуля;
   - `reports/industrial_validation/SCADA_INTEGRATION_REPORT.md` — версия Ignition, конфигурация, карта регистров,
     методика, результаты каждого испытания с цифрами, ограничения (trial, локальный контур, MasterSCADA не
     проверялась), что осталось;
   - `reports/industrial_validation/evidence/scada/` — скриншоты, CSV-журналы (урезанные до разумного объёма),
     выдержки логов, результаты сравнения;
   - обновлённая матрица требований — новым файлом (например,
     `reports/industrial_validation/REQUIREMENTS_TRACEABILITY_MATRIX.csv`, исключение для него уже есть
     в `.gitignore` на ветке `next-gen/platform`; на своей ветке добавь
     `!reports/**/REQUIREMENTS_TRACEABILITY_MATRIX*.csv` после `*.csv`), пересчёт оценки тем же способом, что
     `reports/remediation/tests/build_rtm.py`. REQ-API-07 переводить в PASS только при полном комплекте
     доказательств; при частичном — PARTIAL с объяснением. REQ-CV-05 не трогать. Ожидание: если закрыть только
     REQ-API-07, оценка вырастет меньше, чем до 99,46 (это значение — при закрытии обоих) — посчитай точно.
9. **Регрессия:** полный `pytest` до и после изменений (результаты в отчёт), проверка, что при
   `GAUGEVISION_MODBUS_ENABLED=0` поведение прежнее, WSS/авторизация/QR не затронуты.
10. Логичные коммиты по шагам, `git push -u origin next-gen/scada-ignition`. В конце — отчёт пользователю:

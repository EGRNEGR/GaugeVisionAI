# Заметки по коду GaugeVision AI (факты для лендинга)

Все ссылки вида `файл:строка` относятся к ветке worktree-gaugevision-landing на 2026-11-14. Версия приложения: 1.0.0 (`app/__init__.py:3`).
Пути: `app/config.py` (C), `app/vision.py` (V), `app/streamer.py` (S), `app/main.py` (M), `app/db.py` (D), `app/discovery.py` (Dis), `static/js/capture.js` (Cap).

## 1. Конвейер по коду

### 1.1 Захват кадра
- Источники: `device` (USB), `rtsp`, `http_mjpeg`, `phone_ws` (`C:122`, `M:56`).
- RTSP, HTTP/MJPEG и USB читает `CaptureWorker` в отдельном потоке `threading.Thread` (`S:204-220`, цикл `_run` `S:281-341`). Бэкенд FFMPEG для rtsp/http (`S:253`), DSHOW на Windows и V4L2 на Linux для USB (`S:244-246`).
- Буфер драйвера 1 кадр: `cap.set(CAP_PROP_BUFFERSIZE, CAPTURE_BUFFERSIZE)`, `CAPTURE_BUFFERSIZE = 1` (`C:67`, `S:260`). В комментарии назван «Zero Latency Mode».
- Тайм-ауты открытия и чтения 6000 мс (`S:233-235`). RTSP по TCP, `stimeout` 5 с (`S:40`).
- `FrameBroker` хранит только последний кадр каждой камеры (`S:63-120`, `publish` `S:70-78`). Анализ не работает со «застоявшимся» буфером.
- Смартфон: `PhoneWorker` (`S:347`). Кадры приходят по WSS в `ws_phone` (`M:746-798`), декодируются через `cv2.imdecode` в `run_in_executor` (`M:740-743`, `M:774`), затем `worker.push_frame` (`S:367`). Лимит кадра 8 МиБ (`M:770`).
- Асинхронность: сервер на FastAPI/asyncio. Цикл обработки каждой камеры `GaugeService._process_loop` (`M:300-324`) берёт свежий кадр, только если номер кадра новый (`M:313`), и считает его в `ThreadPoolExecutor` с `VISION_EXECUTOR_WORKERS = 2` (`C:73`, `M:217`, `M:315-316`). Частота `PROCESS_FPS = 3.0` (`C:51`, `M:303`).
- Кадры шире `MAX_PROCESS_WIDTH = 1280` уменьшаются с `INTER_AREA` перед анализом (`C:61`, `V:898-900`).

### 1.2 Локализация (YOLO и резервный путь OpenCV)
- Загрузка YOLO ленивая, из локальных весов `models/gauge_yolov8.pt` (`C:27`, `V:85-108`). Прогрев пустым кадром 640×640 (`V:100-101`). Если файла нет или `ultralytics` не импортируется, `_YOLO = False` и работает OpenCV (`V:92-93`, `V:105-107`). Загрузка идёт вне event-loop при старте (`M:233`).
- Устройство: `auto` берёт CUDA при наличии, иначе CPU (`V:53-68`). На GPU включается FP16: `quantize=16` для новых версий ultralytics или `half=True` для старых (`V:71-82`).
- Параметры: `YOLO_IMGSZ = 640`, `YOLO_CONF = 0.35` (`C:32-33`, `V:127`). Инференс под `_YOLO_INFER_LOCK`, так как предиктор не потокобезопасен (`V:47`, `V:126`).
- Берётся самый крупный бокс из классов, в имени которых есть `gauge`, `dial`, `meter`, `manometer`, `clock` (`C:29`, `V:120-143`). Класс `Needle` модели в конвейере не используется (в `YOLO_CLASSES` его нет).
- `detect_dial` (`V:379-402`): YOLO и контурный OpenCV считаются оба. Если центр эллипса OpenCV внутри бокса YOLO ± 15 % и большая полуось в диапазоне 0,25–1,6 от max(w,h) бокса, берётся эллипс (`source = "yolo+ellipse"`, `score ≥ 0.97`) (`V:393-401`). Иначе `_roi_from_yolo_bbox` (`V:345-355`): отступ 8 %, эллипс внутри бокса, иначе эллипс, вписанный в бокс (score 0.95 или 0.9).
- Резервный путь `_find_dial_opencv` (`V:286-334`): CLAHE, затем `GaussianBlur(9×9, σ=2)` (`V:294`), `HoughCircles(HOUGH_GRADIENT, dp=1.2, minDist=0.35·short, param1=140, param2=45, minRadius=max(25, 0.10·short), maxRadius=0.60·short)` (`V:296-302`).
  - Основной выбор делает эллипс по контуру (`_ellipse_candidates`, `V:245-283`). HoughCircles только подтверждает: совпадение центров в пределах 10 % большой полуоси даёт score 0.95, иначе 0.75 (`V:319-324`). Из концентрических кандидатов выбирается внутренний, то есть шкала (`V:309-317`).
  - Если эллипсов нет, берётся самая крупная окружность Хафа со score 0.6 (`V:327-333`).
- Фильтры `_ellipse_candidates`: `GaussianBlur 5×5`, `Canny(40, 130)`, `dilate 3×3` (`V:251-253`); площадь ≥ 1,5 % кадра (`V:256`); не менее 20 точек контура (`V:258`); полуоси ≥ 15 px и ≤ 0,75·max(h,w) (`V:271`); отношение осей ≥ 0,45 (`V:274`); заполнение площади эллипса 0,75–1,25 (`V:278`).
- Крайний резерв `frame_roi`: круг радиусом 0,47·min(h,w) в центре кадра, score 0.3, `source="frame"` (`V:358-362`). Ручная область `manual_roi` из калибровки в долях кадра (`V:365-376`).

### 1.3 Нормализация (эллипс → круг)
- `roi_from_ellipse` (`V:197-223`): аффинная матрица `M = T(S/2)·R(φ)·diag(R/a, R/b)·R(−φ)·T(−c)`. Растяжение идёт вдоль осей эллипса, а ориентация шкалы сохраняется, поэтому углы стрелки остаются в системе координат кадра.
- `normalize_dial` (`V:226-232`): `cv2.warpAffine`, `INTER_LINEAR`, `BORDER_REPLICATE`, результат 640×640 (`C:50`, `DIAL_SIZE = 640`).
- Это аффинная, а не проективная коррекция. Полной гомографии в коде нет.

### 1.4 Коррекция освещения и выделение стрелки
- CLAHE: `createCLAHE(clipLimit=3.0, tileGridSize=(8, 8))` в `_prep_gray` (`V:238-242`). Используется только при поиске циферблата (`V:291`, `V:351`). В масках стрелки CLAHE нет.
- `needle_masks` (`V:426-443`):
  - серый канал, `GaussianBlur 5×5` (`V:431-432`);
  - Black-Hat (тёмная стрелка на светлом фоне) и Top-Hat (светлая на тёмном) с эллиптическим ядром 31×31 (`_HAT_KERNEL`, `V:412`, `V:433-434`);
  - третья маска «saturation»: канал S в HSV, `GaussianBlur 5×5`, Top-Hat с тем же ядром (для цветных, например красных, стрелок) (`V:436-442`).
- `_hat_mask` (`V:416-423`): порог Otsu считается только по пикселям кольца 0,04–0,46 размера циферблата (`_ANNULUS`, `V:411`), нижняя граница порога 18 (`V:420`), затем `MORPH_CLOSE` ядром 5×5 (`V:413`, `V:423`).

### 1.5 Поиск стрелки
- `estimate_needle` (`V:556-588`): для каждой из трёх масок считается радиальный момент, выбирается маска с наибольшей уверенностью (`V:567-572`). Затем HoughLinesP на выбранной маске.
- `_needle_angle_moment` (`V:446-507`): минимум 25 пикселей маски (`V:457`); учитывается кольцо r ∈ (0,06; 0,36)·size, внешние риски и цифры исключены (`V:464`); вес пикселя r/(size/2) (`V:470`); гистограмма по 1° с круговым сглаживанием окном 9 (±4°) (`V:473-476`); второй максимум ищется за пределами ±25° (`V:483-484`); радиальная протяжённость пика в секторе ±6° относительно 0,30·size (`V:486-487`); `confidence = clip((1 − second/peak)·min(1, radial_extent), 0, 1)` (`V:488`); угол уточняется взвешенным круговым средним в ±6° (`V:490-497`); остриё — самая дальняя точка маски в секторе при r < 0,46·size (`V:499-506`).
- `_needle_angle_hough` (`V:510-549`): `HoughLinesP(rho=1, theta=π/360, threshold=0,08·size, minLineLength=0,15·size, maxLineGap=10)`. При size = 640 это порог 51 голос и минимальная длина 96 px (`V:514-517`). Отбор: расстояние линии до центра ≤ 0,06·size (`V:529`); ближний к центру конец ≤ 0,22·size от центра (`V:534`); score = длина·(1 − d/(0,06·size)·0,5) (`V:536`); остриё — дальний от центра конец (`V:546`); `θ = atan2(ty − c, tx − c) mod 360` (`V:547`); уверенность `min(1, score/(0,30·size))` (`V:548`).
- Слияние (`V:577-588`): если Hough и момент расходятся не больше чем на 12°, берётся круговое среднее с весами по уверенностям, `conf = min(1, 0,6·conf_момента + 0,4·conf_Hough + 0,1)`, метод `hough+moment/<маска>`. Иначе результат момента с уверенностью ×0,9, метод `moment/<маска>`. Ведущий метод — радиальный момент, Hough его уточняет.
- Формула угла: `θ = atan2(...)`, в градусах по модулю 360 (`V:469`, `V:547`). Система координат кадра, ось Y вниз: 0° — «3 часа», 90° — «6», 180° — «9», 270° — «12» (`V:23-25`).

### 1.6 Калибровка угол → значение
- `angle_to_value` (`V:606-633`).
  - CW: `Δθ = (θ − θmin) mod 360`, `span = (θmax − θmin) mod 360` (`V:619-621`).
  - CCW: `Δθ = (θmin − θ) mod 360`, `span = (θmin − θmax) mod 360` (`V:622-624`).
  - `V = Vmin + (Δθ/span)·(Vmax − Vmin)` (`V:631-633`). Если span ≈ 0, берётся 360 (`V:625-626`).
  - «Мёртвая зона» шкалы: если Δθ > span, угол относится к ближайшему краю (перелёт за максимум или недолёт до минимума) (`V:627-630`).
  - Доля ограничена диапазоном от −0,05 до 1,05 (`clamp = 0.05`, `V:606`, `V:632`): значение может выходить за шкалу на 5 % диапазона.
- Обратное преобразование `value_to_angle` (`V:636-649`) нужно для дуг уставок на оверлее.
- Параметры по умолчанию: Vmin 0, θmin 135, Vmax 10, θmax 45, CW (`D:81-87`, `M:66-72`). Это шкала 270°. Валидация: Vmax ≠ Vmin (`M:81-86`), углы приводятся по модулю 360 (`M:74-79`).
- Единицы проверяются по типу прибора (`M:131-138`).

### 1.7 Стабилизация
- EMA: `EmaFilter` (`V:688-709`), `V̄t = α·Vt + (1−α)·V̄t−1`, α = `EMA_ALPHA = 0.25` (`C:49`, `V:701`). Первое значение берётся как есть (`V:698-699`).
- Порог уверенности: отсчёт достоверен, если `needle.angle_deg` определён и `confidence ≥ MIN_NEEDLE_CONFIDENCE = 0.25` и значение посчитано (`C:62`, `V:916-920`). Иначе `_miss_streak += 1` (`V:922`).
- Удержание значения: `ema.update(None)` возвращает последнее сохранённое EMA (`V:695-697`, `V:924`). `status_level` считается по сглаженному значению (`V:925`). В состоянии `last_valid_ts` сохраняет время последнего достоверного кадра (`M:342`).
- Сброс EMA при смене калибровки (подпись калибровки без `roi`) (`V:903-906`).
- Гистерезис области циферблата: `GaugePipeline._locate` (`V:865-889`). Повторная локализация нужна, если ROI нет, источник `frame`, прошло `REDETECT_EVERY_N_FRAMES = 15` кадров или `_miss_streak ≥ 3` (`C:59`, `V:871-873`). Если новый центр сместился меньше чем на 5 % большой полуоси и `_miss_streak < 3`, остаётся прежний ROI (`V:878-883`). Если ничего не найдено и нет ROI или промахи ≥ 3, ставится `frame_roi` (`V:885-886`).
- REDETECT вручную: `POST /api/cameras/{id}/redetect` вызывает `pipeline.reset()` (`M:635-641`, `V:857-863`).
- Блокировка `threading.Lock` на экземпляр конвейера (`V:854`, `V:895`).

### 1.8 Уставки
- `classify_level` (`V:665-682`): `V ≤ LL` или `V ≥ HH` → `alert`; `V ≤ L` или `V ≥ H` → `warning`; иначе `normal`. Незаданные уставки пропускаются. Поля: `ll_alert`, `l_warn`, `h_warn`, `hh_alert` (`D:72-77`).
- Проверка порядка при сохранении: неубывание по заданным (`M:95-101`, ошибка 422). Допускаются равенства.
- Пять зон отображаются на оверлее как дуги на шкале (`V:738-758`, `V:775-803`). Цвета: normal (90,200,80), warning (0,200,255), alert (50,50,240) в BGR (`V:722`). Бейджи «CRITICAL» и «WARNING» (`V:825-831`).
- Статусов в БД три: `normal`, `warning`, `alert` (`D:65`).

### 1.9 Выдача
- `GaugeService._on_reading` (`M:326-353`) формирует состояние: `value` (EMA), `raw_value`, `angle`, `valid`, `confidence`, `level`, `dial_found`, `dial_source`, `method`, `process_ms`, `last_valid_ts`. Рассылка `{"type": "reading", ...}` всем пультам на каждом обработанном кадре (около 3 раз в секунду на камеру).
- Типы сообщений `/ws/dashboard`: `snapshot` (при подключении, `M:814`), `reading` (`M:345`), `status` (`M:281`), `camera_added` (`M:413`), `camera_updated` (`M:451`), `camera_deleted` (`M:465`), `ack` (`M:836`), `pong` (`M:821`). Клиентский `ping` принимается (`M:820`).
- `DashboardHub` (`M:160-194`): у каждого клиента своя очередь на 300 сообщений (`M:167`) и своя задача-отправитель (`M:807-810`). При переполнении отбрасывается самое старое сообщение (`M:189-194`).
- Запись в БД: только если `valid` и EMA не `None`, не чаще `DB_WRITE_INTERVAL = 1.0` с на камеру (`M:348-353`, `C:52`). Пишется EMA-значение, сырой угол и уровень. Буфер сбрасывается пачкой раз в секунду (`M:366-369`, `D:240-252`, `executemany`). Недостоверные кадры в БД не пишутся.
- SQLite через aiosqlite, одно соединение, `WAL`, `synchronous=NORMAL`, `foreign_keys=ON` (`D:90-99`). Метки времени UTC ISO 8601 с миллисекундами (`D:32-34`). Индексы по `timestamp` и `(camera_id, timestamp)` (`D:68-69`).
- Очистка истории старше `HISTORY_KEEP_DAYS = 90` раз в сутки (`M:371-384`, `D:294-301`).
- CSV: разделитель `;`, заголовок `timestamp_iso8601;value_<ед.>;raw_angle_deg;status_level`, значение с 4 знаками, угол с 2 (`D:269-284`), BOM `﻿` (`M:702`). Имя файла: название прибора и локальное время сервера `%Y%m%d_%H%M%S` (`M:697-699`).
- MJPEG с оверлеем: `GET /api/cameras/{id}/mjpeg`, `multipart/x-mixed-replace`, частота `MJPEG_FPS = 8.0` (`M:653-676`, `C:60`). Оверлей сжимается до ширины 960 px (`PREVIEW_MAX_WIDTH`) и JPEG качества 78 (`M:293-296`). При отсутствии кадра отдаётся картинка «NO SIGNAL» (`M:521-527`).
- Квитирование: `POST /api/alarms/ack` рассылает `{"type": "ack"}` всем пультам (`M:831-837`). Сирена и интерфейс квитирования реализованы в `static/js/app.js` (в этих заметках не разбирался).

## 3. Расхождения README ↔ код

Расхождения и недосказанности, которые влияют на формулировки лендинга:

1. **Таймаут смартфона.** README (раздел про смартфон): «Если кадров нет дольше 6 с, камера получает статус «офлайн»». В коде через 6 с (`PHONE_TIMEOUT`, `C:71`) статус становится `reconnecting` (`S:387-392`). Статус `offline` ставится только через 30 с без кадров и при отсутствии подключённых клиентов (`S:350`, `S:393-395`).
2. **Тесты.** README и PRODUCT.md: «e2e-набор сервера (34 проверки) и браузерный тест (18 проверок)». В репозитории тестов нет. Есть только файл `test` в корне размером 6 байт, содержимое «test». Заявление не проверяется кодом.
3. **Замеры не воспроизводятся из репозитория.** Нет датасета, скриптов обучения, бенчмарков, записей замера 0,38 % и 28 сцен. Эти цифры подтверждаются только текстом README.
4. **Ответ сервера 3–37 мс.** В коде это не серверная метрика. На клиенте RTT считается как время от отправки кадра до подтверждения `ack` (`Cap:269`, вывод `Cap:367`). На скриншоте клиента виден «RTT 37 мс». Значение 3 мс в репозитории нигде не подтверждено.
5. **CLAHE и «блики».** В таблице «Ограничения» CLAHE указан как защита от бликов и копоти. В коде CLAHE применяется только при локализации циферблата (`V:241`, `V:291`, `V:351`). В масках стрелки (Black-Hat/Top-Hat/saturation) его нет. Специальной обработки копоти нет.
6. **Третья маска.** README упоминает только Black-Hat и Top-Hat. В коде есть третья маска по насыщенности (HSV S, Top-Hat) для цветных стрелок (`V:436-442`).
7. **Роль Hough.** README в шаге 3 перечисляет Black/Top-Hat, HoughLinesP и радиальный момент как равноправные. В коде ведущий метод — радиальный момент, Hough его уточняет, только если разница углов ≤ 12°; иначе результат момента с уверенностью ×0,9 (`V:577-588`).
8. **Резервный путь.** README: «CLAHE + HoughCircles + контур». В коде основной выбор делает эллипс по контуру, HoughCircles подтверждает или служит последним вариантом (`V:305-333`). Резервный путь также включается, если YOLO загружена, но не нашла прибор (`V:388-391`).
9. **Формула калибровки.** README приводит формулу без допущений. В коде есть ветка CCW, обработка «мёртвой зоны» и допуск ±5 % за пределами шкалы (`V:622-632`).
10. **WebSocket-сообщения.** README перечисляет `status`, `reading`, `camera_added`, `camera_updated`, `camera_deleted`. Код также шлёт `snapshot`, `ack`, `pong` (`M:814`, `M:836`, `M:821`).
11. **Порядок уставок.** README «LL ≤ L ≤ H ≤ HH»: код согласуется (допускает равенство, `M:95-101`). Строка «L < V < H» для нормы согласуется с `classify_level`.
12. **Имя CSV.** Метка времени в имени файла берётся по локальному времени сервера (`time.strftime`, `M:697`), а не по UTC. Метки внутри CSV в UTC.
13. **Структура проекта.** README указывает Chart.js в `static/js/`. В репозитории он лежит в `static/js/vendor/`. В README не упомянут файл `test` в корне.
14. **«Офлайн» не останавливает попытки.** README: «После 8 неудачных попыток подряд камера переходит в статус «офлайн»». Это верно (`S:292`, `S:335`), но цикл продолжает переподключение с паузой 15 с (`S:294-296`), пока камера не удалена или не остановлена.
15. **Буфер 1 кадр.** Верно для RTSP, MJPEG и USB (`S:260`). Для смартфона буфера захвата нет, кадры приходят по WSS. В обоих случаях в `FrameBroker` хранится только последний кадр.

Совпадают с README (проверено): значения `EMA_ALPHA`, `YOLO_CONF/IMGSZ`, `MIN_NEEDLE_CONFIDENCE`, `DIAL_SIZE`, `PROCESS_FPS`, `DB_WRITE_INTERVAL`, `REDETECT_EVERY_N_FRAMES`, `MAX_PROCESS_WIDTH`; backoff 1→2→4→8→15 с; 8 попыток до «офлайн»; 6 классов; 17 единиц; окна трендов 30/60/120; порты сканирования; RSA-2048, 365 дней, SAN, перевыпуск при смене IP (`cert_gen.py:154`); флаги `run.py`; пропуск 198.18.0.0/15 и link-local (`C:147-156`); API-маршруты; формат CSV.

## 5. Стек и архитектура

### Стек
- Python 3.12, FastAPI (async), Uvicorn[standard], aiosqlite, OpenCV (`opencv-python-headless>=4.9`), NumPy ≥ 1.26, cryptography ≥ 42, qrcode ≥ 7.4 (SVG-QR), ultralytics ≥ 8.1 (YOLOv8n), PyTorch (ставится отдельно, CUDA или CPU) (`requirements.txt:9-20`).
- Клиент: vanilla HTML/CSS/JS (`static/index.html`, `static/capture.html`, `static/js/app.js`, `static/js/capture.js`, Chart.js в `static/js/vendor/`). В `index.html` и `capture.html` внешних `http(s)://` ссылок нет (проверено поиском).
- Исходящий трафик в интернет: код не отправляет. Адрес 8.8.8.8 в `config.candidate_lan_ips` используется только как цель `connect()` на UDP-сокете для выбора интерфейса, пакеты не уходят (`C:179-183`). Поведение стороннего `ultralytics` при инициализации в репозитории не проверялось.

### Точки входа
- `python run.py` (`run.py:66-112`): `ensure_certs()` → `config.get_lan_ip()` → баннер → `uvicorn.run("app.main:app", ssl_certfile, ssl_keyfile, ws_max_size=16 МиБ, access_log=False)`. Только HTTPS, порт 8443.
- `app.main:app` — FastAPI-приложение, `lifespan` запускает `GaugeService.start()` (`M:482-502`).

### Модули и вызовы
- `run.py` → `app.config` (константы, LAN IP), `app.cert_gen` (`ensure_certs`, `cert_fingerprint`).
- `app.main` → `config`, `db`, `discovery`, `vision`, `streamer` (`M:46-47`).
  - `GaugeService` создаёт `DashboardHub`, `FrameBroker`, `StreamManager`, `ThreadPoolExecutor(2)` (`M:212-227`).
  - `StreamManager.start_camera` → `CaptureWorker` или `PhoneWorker` (`S:414-421`) → `FrameBroker.publish`.
  - `_process_loop` → `FrameBroker.latest_frame` → `executor` → `vision.GaugePipeline.process` → `FrameBroker.publish_overlay` и `_on_reading` → `DashboardHub.broadcast` и буфер → `db.insert_readings`.
  - REST и WebSocket-эндпоинты → `GaugeService`, `db`, `discovery.discover_all`.
- `app.vision` зависит только от `config`, OpenCV, NumPy и (лениво) `torch`/`ultralytics`.
- `app.discovery` → `config`; `discover_all` параллельно запускает `onvif_discover` и `scan_subnet` (`Dis:361-398`).
- `app.db` → `config`, `aiosqlite`.

### Потоки данных
```
Камера (RTSP/MJPEG/USB) --OpenCV FFMPEG/DSHOW/V4L2--> CaptureWorker (поток) --\
Смартфон (браузер, getUserMedia) --WSS бинарные WebP/JPEG--> ws_phone ---------> FrameBroker (последний кадр)
                                                                                   |
                      _process_loop (3 к/с на камеру) --> ThreadPool(2) --> GaugePipeline.process
                                                                                   |
                       +-----------------------------------------------------------+
                       |                        |                          |
                 broker.publish_overlay   DashboardHub.broadcast     db buffer --1 с--> SQLite (WAL)
                       |                        |                                        |

                       \________________________|________________________________________/
                                           Пульт оператора (браузер)
```

### Протоколы
- HTTPS (Uvicorn с TLS, самоподписанный сертификат RSA-2048 365 дней, SAN localhost/127.0.0.1/LAN IP) — пульт, REST, `/api/docs`.
- WSS: `/ws/dashboard` (JSON), `/ws/phone/{cam_id}?token=` (бинарные кадры, токен `secrets.token_urlsafe(24)`, проверка `compare_digest`) (`S:459-466`).
- RTSP (через OpenCV FFMPEG, транспорт TCP) — вход с IP-камер и NVR.
- HTTP/MJPEG — вход (FFMPEG) и выход (`multipart/x-mixed-replace`, `M:653-676`).
- ONVIF — только WS-Discovery: UDP-мультикаст SOAP Probe на 239.255.255.250:3702, два зонда, TTL 2 (`Dis:293-355`). Дальше предлагается RTSP-URL по вендору (Hikvision, Dahua, Axis) или `rtsp://ip:554/`. Управления по ONVIF (PTZ, профили) нет.
- Сканирование /24: TCP-подключение к портам 554, 80, 8080, 4747, 8554 с протокольной проверкой (`Dis:173-226`).
- SQLite (WAL) локально.
- SCADA-протоколов (Modbus TCP, OPC UA) в коде нет, это Roadmap.

Отсчёт углов на сайте (2026-11-22, по просьбе пользователя):
- Приложение считает θ в координатах кадра от «3 часов» (README). Сайт показывает тот же угол от «6 часов» по часовой: θсайта = (θкадра − 90°) mod 360, чтобы 0° / 360° смотрел вниз, в пустой сектор под шкалой, и стрелка не проходила через шов.
- Та же шкала в отсчёте сайта: θmin 135° → 45°, θmax 45° → 315°, рабочий сектор 270°. Текущий угол со скриншота калибровки 253,4° → 163,4° (4,39 МПа).
